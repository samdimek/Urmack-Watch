4.1 Severity model alignment

Two vocabularies, never conflated: CVSS v4.0 + CWE for vulnerabilities in our own software and dependencies, and our own Critical / Warning / Anomaly economic severity (Doc 01 §6) for invariant breaches — a breach may deserve a Critical page with no CVE in existence. Following Immunefi/Code4rena reporting discipline, every alert carries: affected chain and contract, invariant with expected vs. observed values, block/transaction references, reproduction inputs, confidence and stated limitations, and a private response route. Observed breach, potential exploit, and monitoring/data-quality failure are three distinct labels and never share an alert without saying which is which.

5. Security measures we build with

Platform & tenancy

  • Postgres RLS on every table; org_id scoping; no service_role in request context
  • Cross-tenant isolation tests in CI; RLS pen-test as a Phase 2 gate
  • Supabase Auth (magic link → passkeys → SSO); HTTP-only session cookies; step-up re-auth for routing/severity changes
  • Per-org API rate limits; per-route alert rate caps
  • Cache-Control: no-store on all tenant-bearing responses

Keys & secrets

  • No signing material anywhere — read-only RPC credentials only, scoped per chain
  • GitHub OIDC → cloud secret manager; no long-lived CI keys
  • age/SOPS encrypted local config; quarterly rotation; per-route webhook HMAC keys

Supply chain

  • Lockfile pinning, pnpm audit, Dependabot with review gates
  • CycloneDX SBOM per release + VEX notes for non-affected advisories
  • SLSA v1.2 L1 provenance (→ L2), OIDC-issued build identities
  • KEV-first prioritization for dependency patches; patch SLA by severity

Application

  • ASVS-traced tests: authn, authz, tenant separation, input validation on spec YAML
  • Zod validation at every trust boundary; typed ABIs — no runtime eval of client specs
  • Spec compiler sandboxes assertion evaluation; plans immutable + checksummed
  • Webhook signing with timestamp window; published verify snippets (JS/Python/Go)
  • Structured logging with secret redaction; no payload bodies in logs

Operations

  • OpenTelemetry + evaluation SLO (99.9% of expected ticks); dead-man heartbeat
  • 24-hour shadow-run gate for evaluation-plane deploys
  • PITR Postgres backups, cross-region evidence replication, quarterly restore drill
  • Append-only audit log; quarterly access review
  • Incident runbook with severity-1 path and customer notification templates

Data & disclosure

  • Evidence packs immutable, 90-day retention, 15-min signed URLs, content hash on alert
  • Processor terms + subprocessor list before Beta; retention limits on route payloads
  • Public security contact (security@) with a published disclosure policy (90-day coordinated)
  • Never publish exploitable detail before the protocol has patched

7. Disclosure & incident response duties

  • A vulnerability in Urmack (e.g. an RLS bypass): coordinated disclosure page, 90-day clock, customer notification with evidence of containment; if customer personal data is affected, notify controllers without undue delay.
  • A breach detected in a customer's protocol (our product working): severity-classified alert + evidence pack, IR playbook attach, and — per our disclosure principles — no public detail until the protocol acts.
  • Our own monitoring failure (blind spot): heartbeat dead-man alert, customer notification, post-incident write-up. Reporting our own failures is the trust behavior competitors selling fear cannot copy.
