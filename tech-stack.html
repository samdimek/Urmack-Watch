2.1 Finality policy — the nitty-gritty that decides alert credibility

Block-count depth rules are wrong on L2s. The meaningful states are: sequencer-ordered → posted to L1 → L1-finalized. We model finality as a state attached to every evaluation, and alert latency is decoupled from confidence:

ChainBlock cadenceIntermediate ("safe")Strong finalityUrmack Watch policy
Ethereum12 s slots; epoch = 6.4 minRPC safe tagfinalized ≈ 12.8 min (~64 blocks)Detect on latest, fire Critical immediately, tag the alert provisional; auto-escalate to finalized ~13 min later or retract loudly on reorg
Arbitrum One250 ms orderingBatch posted to L1~15–19 min after L1 batch inclusionDetect on sequencer feed (provisional); confirm when the batch finalizes on L1
BaseFlashblock ~200 ms; L2 block 2 sL1 batch ≈ 2 min≈ 20 minDetect on Flashblock head; confirm on L1 batch finality
Optimism2 s blockssafe = data posted to L115–30 min after submissionSame as Base (shared OP Stack semantics)
Two rules. (1) Alert fast, retract loudly — a Critical invariant breach waits for nothing; correctness of the retraction is what earns trust. (2) The 7-day Standard Bridge withdrawal delay is not transaction finality, and neither is a sequencer's sub-second soft confirmation. Doc 01 §7's heartbeat covers the case where our own view of the head stops moving.

3. The stack, layer by layer

1 · Portal NEXT.JS 15 · TS STRICT · TAILWIND

App Router, server components for dashboards, client islands for the invariant editor (YAML editor + live dry-run results). Auth via Supabase magic link in Phase 1, SSO/SAML for enterprise in Phase 3. Deployment: Vercel (or Fly for EU residency).

2 · API HONO

Fetch-standard typed routes: orgs, protocols, contracts, specs, routes, alert query. Runs on Node 22 (Fly) — same binary type as workers, one Dockerfile. Zod-validated bodies, OpenAPI generated from routes. GET responses carrying tenant data send Cache-Control: no-store.

3 · Spec compiler YAML → PLAN

packages/spec-lang: YAML spec → JSON Schema → Zod-validated evaluation plan (a viem multicall payload + assertion function + finality policy + thresholds). Plan versions are immutable and checksummed; the evaluator never reads YAML at runtime.

4 · Scheduler NODE · REDIS

Subscribes to block headers per chain (viem watchBlockNumber with polling fallback). On tick: claim each due plan via SET NX PX lock, enqueue on BullMQ. Emits heartbeat if now − last_eval > 3 × interval.

5 · Evaluator workers BULLMQ · VIEM

Pull job → build consistent snapshot at one block number (batched eth_call multicall3 + bounded getLogs window) → run assertion (point-in-time / temporal / derived) → write result (pass and margin) → if breach, hold until finality state allows and hand to router. Horizontal scale = more workers; one plan in flight at a time.

6 · Alert router TYPESCRIPT

Severity classification → dedup key (spec_id + breach_kind) → cooldown → evidence pack assembly → fan-out adapters (webhook HMAC-SHA256 over ts.body with 5-min replay window; Telegram/Discord/Slack bots; PagerDuty Events API v2; Resend email; WhatsApp Cloud API on premium). Retries: 5× exponential with jitter; dead-letter to the alert record.

7 · Storage SUPABASE · TIMESCALE · R2

Postgres + RLS for tenancy/specs/alerts/audit; Timescale hypertable evaluation partitioned by plan, retention policy 90 d raw / 2 y hourly; Upstash/Redis for locks and circuit breakers; Cloudflare R2 (or S3) for immutable evidence packs with 15-minute signed URLs.

3.2 Local development & environments

  • Anvil (Foundry) fork of Ethereum mainnet for integration tests — a fixture protocol with a deliberately breakable invariant (drain the reserve, skew the share price) proves the whole pipeline end-to-end in CI.
  • Three environments: local (docker-compose + Anvil) · staging (real RPC, synthetic protocol, no real routes) · prod. Spec fixtures and alert-route fixtures are shared via seed scripts.
  • CI gates: tsc --noEmit, ESLint, Vitest unit + Anvil integration, RLS policy tests (two tenants, cross-tenant read must 404/403), and a 24-hour shadow run of the scheduler before any production deploy touching the evaluation plane.

4. Data acquisition: RPC-first, indexers optional

The product's critical path reads current state: balances, ratios, share prices, privileged-role changes. That is eth_call + getLogs work, not a graph query. Building on an indexer would mean our alerts depend on a third party's sync lag — unacceptable for a product whose promise is "we tell you the moment an invariant breaks".

Rule: nothing on the alert path may have a sync lag we do not control. The indexer earns its place only after Phase 1, and only where it demonstrably removes RPC load.

5. The spec language and evaluation loop (the actual product)

Everything above is plumbing. The asset is the language and the engine:

# invariant: eth-solvency-usdc — declarative, human-auditable
name: Reserve solvency (USDC vault)
protocol: acme-vault
kind: point_in_time            # point_in_time | temporal | derived
cadence: 60s
severity: critical
observe:
  assets:   { call: "totalAssets()" }
  liabilities: { call: "totalLiabilities()" }
assert: assets >= liabilities * 1.02   # 2% safety band → Warning at 1.05
temporal: holds_for: 3_blocks           # suppresses single-block noise
finalize: alert_at: provisional         # confirm_at: finalized (§2.1)
  1. Compile. Resolves contract addresses + proxies, expands observe into a multicall3 payload, type-checks return types against the ABI, emits EvalPlan{version, checksum}.
  2. Dry-run gate. The plan replays over 7 days of history; a spec that fails or throws cannot be armed. This is the false-positive firewall.
  3. Arm. Scheduler picks it up at its cadence; every evaluation — pass or fail — writes (plan, block, ts, values, pass, margin).
  4. Breach. Hold to finality policy → classify → dedup/cooldown → evidence pack → route. Margin history powers the "how close did we come?" chart, which is the feature that keeps customers after the adrenaline fades.

6. Security & multi-tenancy nitty-gritty

ConcernImplementation
Signing materialNone. Ever. The product holds read-only RPC credentials only; no wallet, no signer, no key-management service is provisioned in any environment.
Tenant isolationPostgres RLS on every table with org_id; the API's DB role is not service_role in request context; cross-tenant probes are a CI test, and an RLS pen-test is a Phase 2 exit gate.
SecretsGitHub OIDC → cloud secret manager (no long-lived CI keys); age/SOPS-encrypted repo config for local dev; provider keys scoped per chain and rotated quarterly; webhook HMAC keys per route.
Supply chainpnpm lockfile + pnpm audit in CI, Dependabot/Renovate, SBOM per release, no postinstall scripts from new deps without review.
AuditabilityAppend-only audit_log (who changed a spec/route/severity, with before/after); alert status transitions (open → acked → resolved / false-positive) are part of the audit trail.
Evidence objectsImmutable, 90-day retention, 15-min signed URLs, served no-store; exportable as a bundle for IR retainers.
Abuse resistancePer-org rate limits at the API, per-route alert rate caps, re-auth (step-up) for routing/severity changes.

7. Integration & delivery nitty-gritty

Outbound (alert channels)

  • Webhook: POST JSON, headers X-Urmack-Signature: sha256=…, X-Urmack-Timestamp (±5 min), X-Urmack-Alert-Id as idempotency key; verify snippet published in docs for JS/Python/Go.
  • Retries: 5 attempts, exponential backoff + jitter, then DLQ → visible as delivery_failed on the alert, not silent.
  • PagerDuty: Events API v2, severity mapping Critical→critical, Warning→warning.
  • Telegram/Discord/Slack: bot per workspace; message contains severity, invariant, observed vs. threshold, block, link to evidence.
  • WhatsApp Cloud API: premium tier only, template messages, opt-in captured in portal.
  • Inbound: Slack interactivity (ack/resolve from the channel) writes back through the API with signed verification.

Control & operations

  • Auth: Supabase Auth (magic link → passkeys → enterprise SSO). Session in HTTP-only cookie; no tokens in localStorage.
  • Billing: Stripe — flat platform fee + metered overage (evaluations beyond plan cadence, chains beyond plan count); webhook → billing_status with grace-period degradation (degrade cadence, never delete data).
  • Observability: OpenTelemetry traces across scheduler → worker → router; RED metrics per plan; Grafana Cloud alert on our own eval SLO (99.9% of expected ticks completed) plus dead-man on heartbeat.
  • Feature flags / config: env-driven per-environment config, no hard-coded chain lists — chains are rows in a chain_config table.
  • Backups: PITR on Postgres, cross-region R2 replication for evidence, quarterly restore drill recorded in the runbook.

8. Packaging & price sanity-check

Competitive reference points (Oct 2026): Forta sells token-denominated subscriptions (General Plan announced at 250 FORT/mo; Premium Feeds priced per feed) — no transparent USD anchor. Hypernative is demo/quote-led with no public price. Tenderly alerts are paywalled, sales-gated. Chainlink Automation was deprecated in mid-2026 (CRE is the successor), removing the one gas-plus-premium incumbent reference. No competitor publishes a clean "economic invariant monitoring" price — which is the opening.
