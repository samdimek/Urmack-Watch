1. Product definition

Problem. Audits are point-in-time. Between engagements, protocols drift: an upgrade shifts accounting, an oracle degrades, a privileged role is abused, liquidity hollows out. Existing monitoring (Forta-style node alerting, Tenderly alerts) watches transactions and log patterns; it does not evaluate whether the protocol's economic rules still hold.

Product. A multi-tenant SaaS where a protocol team declares invariants — properties that must always be true (solvency, share-price bounds, collateral ratios, conservation of funds) — and Urmack Watch continuously evaluates them against live chain state. A breach produces a severity-classified alert with a full evidence pack, not a raw log line.

Buyer. Protocol founders/CTOs, DAO security working groups, and (Tier 3) funds buying portfolio coverage.

Mooat. Urmack's research practice supplies the invariant library and the economic reasoning behind severity classification — the part general-purpose monitoring cannot commoditize.

3. System architecture

Seven bounded contexts. Every component is independently deployable; the evaluation plane (3–6) is isolated from the control plane (1–2, 7) so portal traffic can never starve monitoring.

1 · Control API CONTROL PLANE

REST/JSON API for orgs, users, protocols, contracts, invariant specs and notification routes. Supabase Auth (magic link → later SSO) + Postgres with row-level security as the hard multi-tenant boundary.

2 · Onboarding & Spec Compiler CONTROL PLANE

Validates addresses/ABIs, resolves proxy implementations, compiles the human-readable invariant spec (YAML) into an evaluation plan: the exact eth_call batch, storage reads, event queries and the assertion function. Runs a dry-run backfill over N historical days to prove the invariant before arming.

3 · Scheduler EVALUATION PLANE

Block-height-driven tick service (per chain). Emits evaluation jobs per protocol/plan at the subscription cadence (Tier 1: 5-min · Tier 2: per-block). Guarantees exactly-one-in-flight per plan via Redis locks; missed ticks feed the heartbeat (§7).

4 · Chain Data Layer EVALUATION PLANE

Multi-provider RPC pool (Alchemy/QuickNode + fallback) with per-chain adapters, confirmation-depth handling (default 2 blocks L1 / 1 block L2), reorg detection, and a cached ABI/implementation registry. Read-only keys only — the product never holds signing material.

5 · Snapshot & Evaluation Engine EVALUATION PLANE

Builds a consistent state snapshot per tick (batched eth_call + event window), then executes the compiled assertions: point-in-time, temporal ("X holds for N consecutive blocks"), and derived-metric checks (ratios, share-price math). Emits EvaluationResult{plan, block, values, pass, margin}.

6 · Detection, Severity & Alert Router EVALUATION PLANE

Classifies breaches (Critical / Warning / Anomaly per §6), applies dedup + cooldown (no alert storms), packages the evidence pack (§8), and routes to channels: webhook (HMAC-signed), Telegram, Discord, Slack, PagerDuty, email — WhatsApp via Cloud API on the premium tier.

7 · Client Portal CONTROL PLANE

Next.js app: protocol health dashboard, invariant editor with live dry-run, alert history with evidence viewer, routing config, team management. Read/write only through the Control API.

Supporting data services

  • Postgres (Supabase, RLS) — tenancy, specs, plans, alert records, audit log.
  • TimescaleDB hypertables — every EvaluationResult (pass or fail) as time-series: powers margin charts ("how close did we come?") and post-incident timelines.
  • Redis — tick locks, provider circuit breakers, hot ABI cache.
  • Object store (S3/R2) — evidence packs (immutable, 90-day retention; exportable for IR retainers).

7. Failure modes & mitigations

FailureMitigation
RPC provider outageMulti-provider pool with circuit breakers; degrade cadence rather than skip; if no evaluation within 3× expected interval, heartbeat dead-man alert — the monitor reports its own blindness.
Chain reorgFinality depth per chain (configurable); breach alerts wait for depth, sub-depth violations recorded as pending.
Spec author errorDry-run backfill (§2) before arming; plans are versioned and immutable; changing a spec never rewrites history.
False-positive stormDedup + cooldown + per-route rate caps; anomaly channel never pages.
Tenant data leakPostgres RLS on every table; evidence objects signed-URL only; quarterly access review; RLS pen-test is a Beta gate.
Insider compromise of UrmackNo signing keys ever stored; read-only RPC credentials scoped per provider; alert routing changes require org-owner re-auth and are audit-logged.

8. Evidence pack (the product's differentiator)

Every Critical/Warning alert ships a signed, self-contained bundle: (1) breached invariant in human language + raw spec, (2) evaluated values vs. thresholds at breach block, (3) 24 h margin time-series, (4) the triggering transaction(s) with decoded traces, (5) recent privileged events on in-scope contracts, (6) Uremack first-checks playbook. This is the artifact that turns an alert into an engagement and feeds the IR retainer upsell.

9. Scaling path

v1: single evaluation worker pool, protocol-level partition keys. v2: per-chain partitions, snapshot caching across protocols sharing an RPC provider, spec-level precomputation. v3: portfolio tier — one evaluation pass amortized across funds' overlapping protocol sets. Timeseries retention: full resolution 90 d, hourly rollup 2 y (hypertable policies).

10. Explicit non-goals (v1)

  • No transaction simulation or auto-response (no signing material — ever).
  • No off-chain data sources (CEX prices, team comms) — on-chain state only, stated plainly in docs.
  • No claim of complete exploit detection. The docs will say what the product does and does not see, matching Urmack's disclosure principles.
